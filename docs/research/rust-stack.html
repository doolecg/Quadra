Rust stack for Quadra, one pick per layer

Researched 2026-10-27. Crate versions and dates come from the crates.io API and GitHub; links are given per claim. Anything I could not confirm is marked UNVERIFIED. "Pros/cons" that are not sourced are my judgement.

Read this first

  1. UI: egui 0.37 with egui_dock. Rerun, a dense shipping viewer, is built on egui. Weak spots: IME and the 0.x API churn.
  2. Viewport: wgpu 30, dropping to raw Vulkan only if a measured limit forces it. No public benchmark of 10M to 50M triangles on wgpu was found (UNVERIFIED); the closest numbers are in the evidence block in section 2, so a prototype is still the first task.
  3. Scene and modifiers: custom dependency graph with lazy evaluation on rayon and a cache per modifier. Not an ECS.
  4. Undo: persistent (shared-structure) scene state with Arc mesh buffers. Undo is a pointer swap. Autosave serialises an immutable snapshot on another thread.
  5. Geometry: own half-edge edit mesh, manifold for booleans, OpenSubdiv for subdivision. All three are C++ except our own mesh, and we already carry C++ for Cycles.
  6. Scripting: embedded Python via PyO3. Plugin API: versioned C ABI, with Wasm as an optional sandbox later.
  7. Files: USD native through the pure-Rust openusd crate (0.8.0), ufbx for FBX, tobj, gltf. Alembic has no good Rust option.
  8. Biggest risks: egui IME, wgpu at 50M+ triangles, openusd being young (v0.8), and many C++ build dependencies.

Performance evidence (second pass, 2026-10-27)

No public number exists for 10M to 50M triangles drawn through wgpu with a real GPU frame time. What I found:

  • Bevy meshlets (runs on wgpu): a scene of 3092 Stanford Bunnies at 144,042 triangles each (about 445 million source triangles, my multiplication) took about 2.78 ms of GPU time per frame on an RTX 3080 locked to base clock, at 2240x1260, averaged over 10 frames. Most of it was the first raster pass (1.85 ms). The renderer picks level of detail, so it does not draw all 445 million. The author says wgpu has no mesh shaders, so this uses indirect draws. Limits: experimental, opaque materials only, slow one-off mesh preparation, memory heavy (jms55 write-up, Bevy 0.14, MeshletPlugin docs). I found no published Bevy 0.15 or 0.16 numbers.
  • Plain Vulkan, GPU-driven (not wgpu): the vkguide demo drew a city of 125,000 objects, over 40 million triangles across two mesh passes (main view and shadow view), at 290 FPS on an RTX 2080; CPU work under 0.5 ms (vkguide, marked outdated by its author).
  • wgpu CPU cost of multi-draw: one multi_draw_indirect call with 100,000 draws took about 2.7 to 3.5 ms of CPU time on an Apple M3 Pro. This is CPU recording and submit only (wgpu PR #10639).
  • Rerun: its viewer is built on wgpu with its own re_renderer and egui (ARCHITECTURE.md). I found no published frame times for millions of points. rend3: no benchmark numbers found.
  • egui with dense UI: no measured numbers found. egui rebuilds the whole UI every frame, so dense lists must only build visible rows (ScrollArea::show_rows). A tree of thousands of nodes needs a flattened visible-rows list first. That is advice from docs and forum posts, not a measurement (ScrollArea docs). Profile with the app's own scenes.
  • rayon: the bvh crate lists a BVH build for 120,000 triangles at 37.4 ms single-threaded and 8.9 ms with rayon (about 4.2 times faster); at 12,000 triangles about 2.7 times, at 1,200 about 1.9 times (bvh 0.12.0 docs, author's own benchmark). A general rayon case study got only about 2 times on 8 threads (4 cores) until the author changed the design (Endignoux). No rayon benchmark on mesh editing at million-triangle scale was found.

Reading: Bevy's number shows wgpu can run GPU-driven cluster rendering of a very large source scene in a few milliseconds, but only with level of detail. It is not proof for 50M triangles drawn at full detail with edit-mode overlays. The prototype stays.

Techniques (design notes, not benchmarks)

For 50M+ triangles: instance repeated objects; run frustum and occlusion culling in a compute pass that writes indirect draw arguments; draw with multi-draw-indirect-count; split big meshes into meshlets with meshopt 0.7.0 (crates.io, binds meshoptimizer, MIT). Selection highlight and picking: render an ID buffer and read back one pixel for picking, and run an edge filter on the ID or depth buffer for the outline. These are standard methods and I did not find a Rust reference implementation to cite.

Pick: wgpu. Why: one code path for Windows, Linux and Mac, feature coverage includes multi-draw-indirect-count and mesh shaders, and it is what egui and Rerun already use. Risk: wgpu overhead at extreme scale; mitigate with a one-week prototype (50M triangles, GPU culling) before locking in, and keep the renderer behind a trait so a Vulkan-only backend could replace it.

Persistent structuresrpds 1.2.1 (2026-05-15), MIT; imbl 7.0.2 (2026-09-09), the maintained successor of im, which is archived (rpds, imbl, im-rs archived)An edit creates a new root that shares unchanged parts. Pick: persistent scene state (imbl or rpds) with copy-on-write Arc mesh buffers. Unlimited steps cost only the changed parts. Autosave: the snapshot is immutable, so a worker thread can serialise it while the UI keeps editing, with no lock. Binary format option: rkyv 0.8.18 (crates.io), UNVERIFIED fit. Risk: memory growth for huge edits (a full-mesh edit keeps two copies); add an optional on-disk spill for old steps. Keep a command log only for labels ("Extrude"), not for reversal.

Rust plugin ABI

abi_stable 0.11.3 was last released 2023-10-12 (crates.io). stabby 72.1.16 (2026-07-20), EPL-2.0 or Apache-2.0, is active but its version number moves fast (crates.io). Rust has no stable ABI of its own. A plain extern "C" table of function pointers with a version field is the simplest and works from any language.

Pick: embedded Python through PyO3 for scripting; versioned C ABI for native plugins; consider Wasm components later for untrusted plugins. Risk: Python start-up time and the cost of crossing the GIL for per-vertex scripts. Provide array (numpy-style) APIs, not per-vertex calls.
