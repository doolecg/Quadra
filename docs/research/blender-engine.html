Blender and Cycles as the render engine for Quadra

Researched 2026-10-27. Every claim has a link. Anything I could not confirm is marked UNVERIFIED. Ratings for speed, stability and effort are my own judgement, not measurements.

Read this first

  1. Latest stable and current LTS are both Blender 5.2.3 LTS (released 2026-10-22). Blender 5.3 is in beta, due about 2026-11-10 (download page).
  2. Blender is GPL. Cycles is Apache-2.0 and can be built alone. Anything that links Blender code (bpy, a fork) forces the whole Rust app to be GPL-compatible.
  3. Recommendation: route C, standalone Cycles linked into the Rust app through a small C++ wrapper. It keeps the app free of GPL, has no Python or Blender start-up cost, and Cycles already has a session API built for live viewport updates.
  4. No Rust bindings for Cycles exist on crates.io, and I found no Rust project that embeds Cycles in-process. The Rust projects I found run Blender as a separate sidecar process. We would write and own a thin C++ layer. This is the main cost. (An earlier version of this page cited a cycles-sys URL; that crate does not exist, see section 3.)
  5. Cycles has no stable public API promise that I could find, and its scene and session code changes often (section 5). Pin one Cycles version and update on purpose. Cycles 5.2.0 is the current tag.
  6. Blender add-ons will not run under route C. Only a separate Blender process (route B) could run them, and that is kept as an optional import and export helper.
  7. V-Ray for Blender is a Blender add-on. Route C cannot load it. Using V-Ray would need a separate deal with Chaos for the V-Ray App SDK.
  8. Licensing points here are a reading of public texts, not legal advice. Ask a UK solicitor before shipping.

Facts behind the table

  • Route A: the PyPI wheel is GPL-3.0, CPython 3.13 only, Windows x64 and ARM64, Linux x64, macOS ARM64 (PyPI). Limits: reload fails, one .blend at a time, other GPU Python modules can block Cycles (bpy docs). Threads: "Python threads are not supported" (threading page). Embedding bpy also fixes our scripting Python at 3.13 and shares one interpreter.
  • Route B: the bpy docs themselves suggest running separate instances and talking by multiprocessing (bpy docs). 5.2 added gpu.init() for background runs (Python API 5.2).
  • Route C: the Cycles repo builds "as a standalone application or a Hydra render delegate" (README). Build uses make update then make, with precompiled libraries for Linux x64, macOS ARM64, Windows x64 and ARM64 (BUILDING.md, lib folder). Input: XML scenes (cycles scene_monkey.xml) (README), with the XML reader in src/app/cycles_xml.cpp (src/app). The Hydra delegate lives in src/hydra (files for mesh, material, light, camera, volume, display driver) and is built by default (WITH_CYCLES_HYDRA_RENDER_DELEGATE ON). It needs USD 25.11 or newer, and Houdini 21+ is supported with Houdini's USD (BUILDING.md).
  • Existing Rust bindings: none found. The URL crates.io/api/v1/crates/cycles-sys answers "crate cycles-sys does not exist" (checked 2026-10-27), so it is evidence of absence, not a crate. The names cycles-rs, cycles-render, cycles-ffi and cycles-render-sys return no crate either; the crates named cycles (a music pattern library) and graph-cycles are unrelated (search). GitHub search found only sidecar uses: agentic-3d-stage (a wgpu viewer with an optional Blender Cycles overlay sidecar), groundwork (a Rust terrain tool that hands rendering to Cycles) and blenderpulse (a render-progress overlay). I found no Bevy or Fyrox experiment that embeds Cycles. Other hosts: hdCycles (Tangent Animation, Apache-2.0, 2020) put Cycles into Houdini as a Hydra delegate; the delegate now lives inside Cycles, and BUILDING.md says it needs Houdini 21+ or USD 25.11+ and must be built against the host's own USD (BUILDING.md). A test repo for PyO3 with bpy 5.0.0 exists (machani-paul007/pyo3-blender-test). Tools we would use for FFI: cxx 1.0.205 and bindgen 0.73.2 (crates.io, crates.io). Because Cycles is a C++ template-heavy API, cxx with a hand-written thin C++ layer is safer than raw bindgen. That is my judgement.
  • Route D: Blender is GPL, so a fork stays GPL (Blender licence page).

4. Licensing

This is my reading of public texts and is a legal opinion, not legal advice. UK law applies to the final shipped product, so get a solicitor to check it before release.

Blender and Cycles

Most Blender source is "GPL version 2 or later"; Cycles is Apache 2.0; all parts are compatible with GPL v3 or later, which is the licence for Blender binaries. Output (images, .blend files) belongs to the user. Published Python scripts using Blender's API must be GPL-compatible (blender.org/about/license). The Cycles repo is flagged Apache-2.0 (GitHub). The bpy wheel is GPL-3.0 (PyPI).

GPL consequences

  • Linking: if a library is GPL (not LGPL), the software that links it must be GPL-compatible as a whole (GPL FAQ: IfLibraryIsGPL). Static or dynamic makes no difference (GPLStaticVsDynamic). So routes A and D make the whole Rust app GPL-compatible.
  • Separate process (route B): the FSF says an "aggregate" of separate programs is allowed, and the line between two programs and one depends on "the mechanism of communication" and "the semantics of the communication" (MereAggregation). Simple fork and exec without "intimate communication" sharing complex data structures keeps programs separate; sharing complex data structures back and forth can make them one program (GPLPlugins). A scene graph sent to Blender is a complex data structure, so route B is a grey area. Ask a solicitor.
  • Route C: Apache-2.0 code can be combined into a proprietary or any-licence app. Keep the licence text and notices. This is the safest.

Recommendation: route C

Use standalone Cycles (route C). Why: it is the only route that keeps our app's licence free, avoids a 200 to 400 MB Python wheel and a Python thread limit, and Cycles already exposes a live session. Keep route B as an optional, clearly separate helper later (for example "import .blend"), run as an unmodified Blender the user installs, with only file-based exchange, which is the cleanest form of separation.

Keeping the viewport live

  • Session runs its own render thread. It offers start(), cancel(), reset(session_params, buffer_params), set_pause(), set_navigating(), set_samples() and ready_to_reset(), and it handles a "delayed reset" and scene updates with locking (session.h).
  • Plan: on each edit, change only the touched Cycles nodes, tag them, then call reset() so progressive sampling restarts. Skip full rebuilds. Whether partial per-object updates are cheap enough for 50M+ triangles: UNVERIFIED, needs a prototype; I found no public measurement. API churn to expect (commit counts from the GitHub API between the tags v4.0.0, v4.5.0 and v5.2.0): src/scene 194 commits to v4.5.0 then 232 to v5.2.0; src/session 27 then 17; src/hydra 25 then 34. Examples: "Refactor: Cycles: Replace new/delete with unique_ptr also for nodes" (bb8190d12) and "Refactor: Cycles: Graphics interop changes" (9d6f2727e). Counts include fixes and cleanups, so they show churn, not the number of breaking changes. The commit dates in this repo look like mirror sync dates, so I give tags, not dates.
  • Display: implement DisplayDriver (methods update_begin, map_texture_buffer, draw, plus graphics-interop hooks) so Cycles draws into our own texture (display_driver.h). Final frames go through an OutputDriver (session.h). The standalone app does the same with OpenGL files in src/app/opengl (src/app).
  • Denoising in the viewport: OIDN is a build option (WITH_CYCLES_OPENIMAGEDENOISE ON), and 5.3 adds a DLSS viewport denoiser on NVIDIA (5.3 Cycles).
